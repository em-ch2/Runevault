# Application database migrations

Spring Boot runs Flyway before JPA. `V1__application_tables.sql` creates the three application tables and the audit ordering index on an empty PostgreSQL database. `V2__reconcile_existing_application_tables.sql` adds historical columns, widens enum constraints, and conservatively classifies older banking outcomes. Hibernate uses `validate` in local and cloud application profiles; it no longer modifies the schema. Tests using H2 disable Flyway and use `create-drop`.

An existing database with application tables but no `flyway_schema_history` is automatically baselined at version 1; Flyway then runs V2 and V3. **Before first startup against existing data**, take and verify a backup, confirm that `transactions`, `device_states`, and `audit_events` are the Runevault tables in the selected schema, and inspect the pending V2 and V3 SQL. Do not point the application at an unrelated nonempty schema: automatic baselining would skip V1. V2 contains no deletes or counter/claim resets. It preserves SIMULATED rows, physical verification evidence, device revocations, counters, claims, and audit rows. Its historical banking-status corrections are intentionally conservative. If migration fails, leave the database intact, diagnose the SQL and data, and restore only from a verified backup into a separate environment; never replace newer counters or claims with stale state.

For a fresh local database, set private credentials in `.env` and run `docker compose up -d --build`. The backend applies V1, V2, and V3 before its readiness probe succeeds. Check `docker compose ps` and `docker compose logs --tail=100 backend`. Inspect `flyway_schema_history` with a database client to confirm versions 1, 2, and 3 succeeded. The container-backed `PostgresMigrationTest` checks empty and legacy PostgreSQL schemas; `PostgresBootstrapSpringTest` checks that Spring starts with Flyway and Hibernate `validate`. CI requires these tests to execute rather than be skipped.

For Tiger Cloud, point `TIGER_JDBC_URL` at the correct database with `sslmode=verify-full` and a verified CA, retain `SPRING_JPA_HIBERNATE_DDL_AUTO=validate`, and start the cloud backend only after reviewing the target schema and backup. Flyway uses the same migrations; no separate Hibernate bootstrap is needed. This procedure does not import local history into Tiger. To move local history, use a reviewed database migration with consistent device keys, counters, revocations, transactions, and audits; never combine independently active databases for the same Pico.

`V3__dashboard_transaction_fields.sql` adds the nullable Gemini decision explanation and confirmed bank balance columns to fresh and existing databases, including those previously maintained by Hibernate. All three migrations run before Hibernate validates the schema; verify versions 1, 2, and 3 in the migration history.

The dashboard's `PipelineEventWriter` initializes `pipeline_events`, its indexes, and optional TimescaleDB aggregates after Flyway completes. These objects are not yet owned by Flyway. Move that bootstrap into new numbered migrations (V4 and later) when coordinating TimescaleDB extension privileges and Tiger Cloud support. Test against empty and upgraded databases. Do not edit an applied migration: Flyway checksums protect the history.

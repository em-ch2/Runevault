# Application database migrations

Spring Boot runs Flyway before JPA. V1 creates the application tables; V2 reconciles historical columns and constraints without deleting transactions, audits, device counters, revocations, or execution claims; V3 adds dashboard fields. V4 owns `pipeline_events` and indexes, and backfills `pipeline_event_keys` for atomic event-ID deduplication. V5 creates a TimescaleDB hypertable and minute aggregate only if the extension is already installed. Plain PostgreSQL retains an ordinary event table. Hibernate validates the schema in local and cloud application profiles. Isolated H2 tests use `create-drop`.

An existing database with application tables but no `flyway_schema_history` is baselined at version 1, then receives V2 through V5. **Before first startup against existing data**, take and verify a backup, confirm that `transactions`, `device_states`, and `audit_events` are Runevault tables in the selected schema, and review each pending migration. Do not point the app at an unrelated nonempty schema: baselining would skip V1. If migration fails, leave the database intact and diagnose the SQL. Never replace newer counters or execution claims with stale backup state.

For a fresh local database, put private credentials in `.env` and run `docker compose up -d --build`. Check `docker compose ps`, `docker compose logs --tail=100 backend`, and `flyway_schema_history` for successful versions 1 through 5 before using the app. `PostgresMigrationTest` checks empty and legacy PostgreSQL schemas; `PostgresBootstrapSpringTest` checks Spring startup with Flyway and Hibernate validation. CI requires these container-backed tests to run.

For Tiger Cloud, configure `TIGER_JDBC_URL` with `sslmode=verify-full` and a trusted CA, retain `SPRING_JPA_HIBERNATE_DDL_AUTO=validate`, and review the target schema and backup before startup. Install the TimescaleDB extension **before V5 runs** if the hypertable and continuous aggregate are desired. Enabling it later does not rerun V5. Verify extension support and aggregate privileges on the target service before deploying. V5 does not modify application transaction or security tables. This procedure does not import local history; any data migration must carry device keys, counters, revocations, transactions, and audits consistently. Never run two independent databases against the same Pico.

Do not edit applied migration files: Flyway checksums protect the history. New pipeline schema changes belong in new numbered migrations.
